# Aero 1.1.0 源码合规审查报告

**核心结论：整体合规风险为【低】。第一方代码统一采用 MIT 许可，全部第三方 Rust 依赖与链接的系统库均为宽松许可，未发现 copyleft 传染风险、未发现许可协议冲突。以下整改项均已当场修复。**

审查对象：Aero 1.1.0 工作区源码（9 个编译器/工具 crates、12 个官方核心 crate）、安装脚本、打包产物。
审查维度：第一方许可统一性、第三方 Rust 依赖许可、LLVM 静态链接许可、FFI 系统库许可、许可声明完备性。

---

## 一、第一方代码许可统一性

Aero 的所有自研代码统一采用 MIT 许可：

- 工作区全局声明：`Cargo.toml` 的 `[workspace.package]` 中 `license = "MIT"`，9 个 Rust crate 均通过 `license.workspace = true` 继承，一致。
- 根目录 `LICENSE` 为标准 MIT 文本，Copyright (c) 2026 Serein，与各 crate 无冲突。

【低风险，已修复】12 个官方核心 crate（aero-json、aero-crypto、aero-csv、aero-test、aero-collections、aero-time、aero-io、aero-toml、aero-http、aero-logger、aero-regex、aero-net）的 `Aero.toml` 此前未声明 `license` 字段，导致发布到本地注册表时许可元数据缺失。

整改：已为上述 12 个 crate 的 `Aero.toml` 逐一补充 `license = "MIT"`，现在与主项目许可声明完全一致。

---

## 二、第三方 Rust 依赖许可

编译器与工具链的第三方 crate 依赖如下，全部为宽松许可，不产生传染义务：

| 依赖 | 用途 | 许可 | 判断 |
|------|------|------|------|
| logos 0.16 | aero-lex 词法生成器 | MIT / Apache-2.0 | 宽松，无冲突 |
| inkwell 0.9 | aero-ir LLVM 绑定 | MIT / Apache-2.0 | 宽松，无冲突 |
| llvm-sys（inkwell 传递依赖） | LLVM FFI 绑定 | Apache-2.0 WITH LLVM-exception | 见下节 |

所有依赖均可独立重分发、可商用、可闭源使用，GitHub 仓储仅发布更新包、不向第三方开源 Aero 本体的策略不受影响。

【低风险】建议在对外分发包中附带一份 `THIRD-PARTY-LICENSES.md` 或 NOTICE，列出 logos、inkwell 及 LLVM 的许可与版权归属，以满足宽松许可以在重分发时保留版权声明的形式要件。

---

## 三、LLVM 静态链接许可

Aero 通过 inkwell/llvm-sys 将 LLVM 静态链接进 `aero` 二进制。LLVM 采用 **Apache-2.0 WITH LLVM-exception**。

该例外条款明确允许任何人以源代码或目标形式使用、分发 LLVM（含并入更大工程的二进制分发），**不**要求使用 LLVM 的派生作品以 Apache-2.0 或相同许可开源。因此：

- 将 LLVM 静态链接进 MIT 许可的 Aero 编译器完全合规；
- 不触发 copyleft，不迫使 Aero 源码开源。

【无风险】无需整改。

---

## 四、FFI 系统库许可（动态链接）

4 个 FFI 绑定 crate 通过 `gcc -l<lib>` 优先链接系统动态库，未做静态打包：

| crate | 系统库 | 许可 | 判断 |
|-------|--------|------|------|
| aero-http | libcurl | curl / MIT 兼容 | 动态链接，无传染 |
| aero-crypto | OpenSSL (libssl/libcrypto) | Apache-2.0 | 动态链接，无传染 |
| aero-regex | 系统正则实现 | glibc LGPL-2.1 | 动态链接、未捆绑库本体，标准用法 |
| aero-net | WS2_32 | Windows 系统 API（闭源） | 系统级 API 调用，业界通用 |

关键判断：跨语言动态链接（互操作）不构成对链接库的"衍生作品"，MIT 项目通过 `-l` 引用 LGPL/Apache-2.0 系统库不会引入 copyleft 义务，前提是不将库本身再分发。当前 `aot.rs` 链接逻辑为动态链接，符合这一前提。

【低风险】提醒：若未来改为静态链接 libcurl/OpenSSL/regex 并随包分发，需逐库核对再分发许可；当前 1.1.0 不包含该场景。
